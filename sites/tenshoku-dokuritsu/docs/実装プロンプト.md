# 独立か、転職か。 Cursor実装プロンプト

Decision Desk テンプレートでサイトを作るときの手順です。1手順につき、新しい Cursor チャットを開き、その手順のプロンプトだけを貼ります。前の手順が完了してから次へ進みます。

このファイルを作った時点では、サイトのコードはまだありません。実装先は `tenshoku-dokuritsu/site/` です。`decision-desk-template/` は上流のまま残します。

公開する記事は、設計書の W1（TD-01 と TD-20、固定ページ、トップ）までです。移行カレンダーは手順10、それ以降の記事は手順12を1本ずつ使います。

## 使い方

1. リポジトリのルートは `jitty-business` です。
2. 新しいチャットで、手順の「プロンプト」から終わりの区切りまでを貼る。
3. プロンプトは、このファイルの「共通制約」と「記事ID対応表」を読んでから作業する、と書いてあります。
4. 完了条件のコマンドが通るまで、その手順を終了にしない。
5. コミットとプッシュは、人が頼んだときだけ行う。

手順1の作業ディレクトリはリポジトリルートです。手順2以降は `tenshoku-dokuritsu/site` です。

## 共通制約

- 編集してよいのは `tenshoku-dokuritsu/site/` だけ。`decision-desk-template/` と、`tenshoku-dokuritsu/docs/` の企画資料は変更しない。
- セットは Binder、質感は flat。`DD_DESIGN_SET` と `DD_FINISH` は付けない。`DD_MODE` は `demo`。`DD_INSPECT` は付けない。
- デザインセットの部品（`src/design-sets/*/components`）に、ロジック、`<script>`、`<style>`、CSS の import を書かない。色と寸法は CSS 変数から取る。部品と記事に、色・余白・角丸の値を直書きしない。
- 記事の `format` は `guide` / `tutorial` / `comparison` / `news` / `opinion` / `interview`。`intent` は `learn` / `compare` / `choose` / `do` / `solve`。日時は `"2026-10-01T09:00:00+09:00"`、日付は `"YYYY-MM-DD"` のように引用符で囲む。
- 棚の `reviewProfile: sensitive`、または記事の `reviewProfile: sensitive` では、`brief.audience`、`brief.scope`、`sources` が1件以上、`lastVerifiedAt`、`review`、`reviewDueAt` が必要。棚の sensitive を、記事側の `standard` では下げない。
- 情報源は、その手順で実際に開いた http(s) のページだけを `src/data/sources.yaml` に書く。`checkedAt` は開いた日。本文の数値・期限・条件は、そのページに書かれているものだけを使い、`<Conditions>` と `<Evidence>` / `<Cite>` で結ぶ。ページに無い金額、日数、割合、採算は書かない。書けない項目は「確認先」と窓口名にする。
- `requiresSpecialist` は付けない。著者に `specialist` を書かない。専門家監修とは表示しない。
- `sample: true` を新しいコンテンツに付けない。`commercial` はすべて false。商品の申込 URL、アフィリエイト URL、`relation: affiliate` は、提携確認が文書になるまで追加しない。
- `nextSteps` と本文の記事リンクは、公開中の記事だけ。`draft: true` の記事、未来の `publishedAt`、まだファイルの無い記事へはリンクしない。TD-05 と体験談は、調査または取材が完了するまで作らない。
- 退職代行、退職給付金サポート、無在庫物販、情報商材、個別の投資商品、保険販売につながる相談、法律家への有償紹介は案内しない。
- 適職診断、個別の税額・給付額・採算を判定する機能は作らない。
- 移行カレンダーの入力値、退職日、開業日、入社日、健康保険の選択、自由入力の検索語を、保存・サーバー送信・アクセス解析に載せない。
- 識別検査（`tests/identity`、`npm run test:identity`、`npm run build:demo`）は完了条件に入れない。
- 画面を変えた手順は、build のあとブラウザでその画面を操作する。スクリーンショット1枚では完了にしない。
- Windows で環境変数を付けるときは `npx cross-env` を使う。

## 手順1 サイト用フォルダを作る

プロンプト:

~~~text
tenshoku-dokuritsu/docs/実装プロンプト.md の「共通制約」を読み、それに従う。このチャットでは手順1だけを行う。

目的: decision-desk-template を tenshoku-dokuritsu/site にコピーし、demo で起動できる状態にする。

作業ディレクトリはリポジトリルート。

- tenshoku-dokuritsu/site が無い、または空のときだけ作る。
- コピーは追跡ファイルだけにする。例: ディレクトリを作ってから `git -C decision-desk-template archive HEAD | tar -x -C tenshoku-dokuritsu/site`。
- site ディレクトリで `npm ci` を実行する。
- `npm run dev` で http://localhost:4321/ が 200 であることを確認し、確認後にサーバーを止める。

禁止:
- decision-desk-template のファイルを変更すること。
- node_modules、dist、dist-demo、.git、.astro をコピーすること。
- サイト名、記事、カテゴリをこの手順で変えること。
- git init、commit、push。

完了条件:
- tenshoku-dokuritsu/site/package.json と package-lock.json がある。
- npm ci が成功する。
- 開発サーバーでトップが 200 になり、止めたあとにプロセスが残っていない。
- 既に site に独自の変更がある場合は、上書きせずに状態を報告して止まる。
~~~

## 手順4 著者と固定ページを書く

プロンプト:

~~~text
tenshoku-dokuritsu/docs/実装プロンプト.md の「共通制約」を読む。作業ディレクトリは tenshoku-dokuritsu/site。このチャットでは手順4だけを行う。

目的: 著者と、初回公開に必要な固定ページを、サイト設計書の役割に合わせて書く。

読むファイル:
- tenshoku-dokuritsu/docs/サイト設計書.md の §1、§3、§8
- src/pages/about.astro
- src/pages/disclosure.astro
- src/pages/privacy.astro
- src/pages/contact.astro
- src/pages/404.astro
- src/content/authors/editorial-team.md
- src/utils/nav.ts

著者 editorial-team.md:
- name: 独立か、転職か。編集部
- kind: organization
- role: 編集部（記事の整理と、制度・条件の確認を担当）
- sample を外す
- specialist は書かない
- 本文は、編集部として公開情報を整理する立場であること。個別の税額、給付額、採算、契約の適法性は判定しないこと。

固定ページは、既存の about / disclosure / privacy / contact と同じ ListLayout で作る。新しいページは src/pages/editorial-policy.astro（/editorial-policy/）と src/pages/disclaimer.astro（/disclaimer/）。

各ページに書く内容:
- about: サイトの役割（50代からの次の働き方を、比べて、選んで、準備する）。対象は早期退職・役職定年をきっかけに会社の外での働き方を考える管理職・専門職。運営主体の正式名称は未記載であり、公開前に記載する、と書く。実在の個人名・法人名は作らない。編集者は当事者の体験を代弁せず、公開情報を整理する。類似する書籍や他媒体とは無関係である、と書く。編集方針、免責、広告、プライバシー、問い合わせへのリンクを置く。
- editorial-policy: 一次情報を根拠にすること。比較は共通の軸と情報時点を揃えること。独立と転職のどちらも無条件の正解にしないこと。更新と訂正は history に残し、日付の自動更新で鮮度を装わないこと。取材とアンケートは実施条件、対象、実施日が揃ってから公開すること。確認担当は編集部であり、専門家監修ではないこと。定期確認は1月と4月、金融・サービス条件は比較記事の公開時と四半期。
- disclaimer: 情報は一般的な整理であり、個別の税額、給付額、採算、契約判断をしない。条件は変わるので、手続きの前に公式窓口で確認する。退職そのものの是非、公務員、完全引退だけを望む人、許認可業種の開業は初期の対象外。
- disclosure: 広告が無い記事と、広告を含む記事を分ける。掲載順は読者の条件との適合と比較基準で決め、報酬順にしない。未提携の間は公式サイトへの通常リンクと確認事項で記事を成立させる。扱わないものとして、退職代行、退職給付金サポート、無在庫物販、情報商材、個別の投資商品の推奨、保険販売につながる相談、法律家への有償直接紹介を書く。TD-19 に当たる退職金の見分け方は、広告なしで書く方針だと書く。
~~~

## 手順10 移行カレンダーを追加する

プロンプト:

~~~text
tenshoku-dokuritsu/docs/実装プロンプト.md の「共通制約」と「記事ID対応表」を読む。作業ディレクトリは tenshoku-dokuritsu/site。サイト設計書 §7 を読む。このチャットでは手順10だけを行う。記事の本文は書かない。

目的: /tools/transition-calendar/ を、ブラウザの中だけで動く確認リストとして追加する。

入力:
- 退職予定日
- 次の働き方: 独立 / 転職 / 未定
- 開業日、または入社日。転職では「入社日未定」を選べる。未定の働き方では、開業日と入社日のどちらも必須にしない
- 退職後の健康保険: 任意継続 / 国民健康保険 / 家族の扶養 / 転職先の保険 / 未定
- 失業給付の利用意向: 利用を検討する / 利用しない / 未定
- 補助: 企業型DCに加入していたか（はい / いいえ / 分からない）。資格喪失日が分かるか。配偶者の年金の確認が必要か（はい / いいえ / 分からない）

出力の列: 手続き名、対象条件、期限または推奨時期、確認先、解説記事、カレンダーへ追加。
期限の種類を文字で分ける。法令等の期限、推奨時期、窓口への確認が必要なもの。未定の読者には条件別の候補を示し、任意継続・国保・扶養をすべて必須の行にしない。

ルールデータ src/data/calendar-rules.yaml の項目:
id、title、applies（働き方、保険、給付意向、DC、配偶者）、anchor（退職日、開業日、入社日、資格喪失日、なし）、rule（確認済みの計算式、または未確認）、holiday、source、checkedAt、reviewDueAt、article（slug。公開中のときだけリンク）、status（verified または unverified）

初期データ:
- 設計書 §7 の表にある項目（離職理由と給付、市場価値・顧問登録、ローン・カード・口座、健康保険、年金・配偶者、企業型DC、雇用保険、開業届、青色申告承認申請、確定申告・住民税）を行として置く。
- status: verified にして日付を計算してよいのは、この作業で国税庁のページを開き、文面を確認できた開業届と青色申告承認申請だけ。確認したら sources.yaml にその URL と checkedAt を足し、ルールの source から参照する。
- 開業届は、2026年以後の開業について、開業日から1か月、という期限にしてはならない。確認したページの期限（開業した年分の所得税の確定申告期限）に合わせる。青色申告承認申請は、原則その年の3月15日と、1月16日以後の開業は開業日から2か月、を別ルールにする。ページの文面と違う場合は、ページを優先し、verified にしない。
- 休日の扱いをページで確認できなければ、日付をずらさず、「窓口で休日の扱いを確認する」と書く。
- 上の2件以外は status: unverified。日付、.ics、Googleカレンダー追加を出さない。確認先だけを出す。
- 住民税は、一律の法定期限として計算しない。
- 雇用保険の起業時の特例は、給付を受けながら事業を続ける仕組みとは別だと、説明文に書く。日数は書かない。
- 企業型DCは、加入が「はい」の人だけに出す。資格喪失日が分からないときは「勤務先へ確認する」とし、退職日から期限を作らない。

計算とファイル:
- 日付計算は src/scripts/calendar.ts と、テストできる純粋関数 src/utils/calendar.ts に分ける。デザインセットの部品には書かない。
- ページは ListLayout または BaseLayout と Frame を使う。入力には label を付ける。キーボードで操作できる。結果は JavaScript が無いときは、入力欄と「結果の計算には JavaScript を使う。手続きの一覧は退職後の手続きの記事で確認する」を出す。その記事が未公開なら、記事名だけにしてリンクしない。
- localStorage、cookie、サーバーへの POST、解析イベントに入力値を載せない。
- .ics は読者の端末へのダウンロード。近くにその説明を書く。
- Googleカレンダーは、確認済みで日付がある行だけ。公式の TEMPLATE URL に手続き名と日付だけを載せる。入力の全文は載せない。
- ナビとフッターに「移行カレンダー」を出す。home.yaml の calendar.href を /tools/transition-calendar/ にし、トップの主CTAを「退職予定日から、移行カレンダーを作る」に切り替える。副CTAの TD-01 は残す。TD-20 はヒーローの主CTAからは外し、移る前後の区画に残す。
- サイトマップにこの URL を入れる。

テスト:
- 固定の退職日、開業日で、verified の開業届と青色申告が設計書の確認結果と一致すること。
- unverified のルールは date が null であること。
- 働き方が未定のとき、独立だけの行が必須にならないこと。

禁止:
- ログイン、会員、入力の自動保存。
- 未確認ルールの日付出力。
- 個別の保険料、税額、給付額の計算。

完了条件:
- npm run check && npm run lint && npm test && npm run build
- ブラウザで /tools/transition-calendar/ を開く。
- 独立、開業日あり、で結果を出す。verified の行だけに日付とカレンダー追加がある。unverified の行に日付が無い。
- 転職、入社日未定、でも結果が出る。
- ページを再読み込みし、直前の入力が残っていない。
- トップの主CTAからこのページへ移動できる。375px で入力と結果が操作できる。
- 確認後にサーバーを止める。
~~~

プロンプト:

